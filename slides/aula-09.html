A especificação como contrato

O agente escreve o HTML, mas o que a tela afirma é definido pela ESPECIFICACAO.md da aula 8. Cada campo da especificação determina um elemento do dashboard.

  • Pergunta e decisão: posição do cartão na narrativa
  • View e colunas: o que o fetch lê
  • Visual escolhido: o gráfico, que o agente não substitui por outro
  • Título que afirma: frase montada a partir dos dados, e não digitada
  • Âncora e suporte na tela: unidade, período, base de comparação e nota

Arquitetura do dashboard

O GitHub Pages apenas entrega os arquivos estáticos. Os dados são buscados no Supabase pelo navegador de quem abre o painel.

Cada view como endpoint da API

const resposta = await fetch( `${SUPABASE_URL}/rest/v1/vw_p09_recompra?select=*`, { headers: { apikey: SUPABASE_KEY, Authorization: `Bearer ${SUPABASE_KEY}` } } ); const linhas = await resposta.json(); // [{"clientes":93104,"clientes_recorrentes":2789,"recompra_pct":3.00}]

O Supabase publica cada view do schema public como um endpoint da API REST. A resposta é uma lista de linhas em JSON, com os mesmos nomes de coluna da view.

Chave publicável × chave secreta

A Project URL e as chaves ficam no Supabase, em Project Settings, na seção API Keys.

Publicável sb_publishable_…

  • Pode constar no HTML e no commit
  • Identifica o projeto; em projetos antigos, é a anon public
  • Lê só o que o grant e o RLS liberam

Secreta sb_secret_… e senha

  • Não deve constar no HTML, em commits, capturas de tela ou prompts
  • Ignora o RLS, de modo que quem a obtém pode escrever e apagar dados
  • Em projetos antigos, é a service_role

Por que a leitura pública é segura aqui

  • estrela.sql liga o RLS nas seis tabelas com uma política apenas de SELECT para anon
  • views.sql cria as views com security_invoker = on e dá grant select a anon
  • Como não existe política de insert, update ou delete, a chave publicável não altera dados
  • Por outro lado, tudo o que o grant libera fica legível por qualquer pessoa; por isso, dados pessoais reais não devem ser publicados dessa forma

Conversão e formatação de números

const taxa = Number(linha.recompra_pct); // 3.00 chega como 3 const brl = new Intl.NumberFormat('pt-BR', { style: 'currency', currency: 'BRL' }); const pct = new Intl.NumberFormat('pt-BR', { minimumFractionDigits: 2, maximumFractionDigits: 2 }); brl.format(Number('13181027.13')); // "R$ 13.181.027,13" pct.format(taxa) + '%'; // "3,00%"

A API já entrega números JSON; Number() funciona como conversão defensiva, caso a view passe a enviar texto. O Intl restitui a vírgula decimal, o ponto de milhar e os zeros que o JSON descarta.

Construção com o agente

Leia @aula-08-seunome/ESPECIFICACAO.md. Crie a pasta aula-09-seunome com index.html, supabase.js, app.js e style.css: um dashboard estático, publicado no GitHub Pages, que responde às 10 perguntas do Chief de Vendas da Olist. Regras: - Dados só pela API REST do Supabase: fetch em SUPABASE_URL/rest/v1/<view>?select=* com os headers apikey e Authorization: Bearer, usando a chave publicável que vou colar em supabase.js. Nunca use chave secreta nem senha do banco. - Nenhum número digitado no HTML ou no JavaScript: valores, títulos e rótulos numéricos saem das linhas da view. - Um cartão por pergunta, na ordem narrativa da especificação. Cada cartão tem título que afirma montado com os dados; subtítulo com unidade, período (jan/2017 a ago/2018) e filtro; o visual da especificação; a nota da âncora tratada; e a fonte com o nome da view. - Converta valores com Number() e formate com Intl.NumberFormat('pt-BR'). - Chart.js 4 de https://cdn.jsdelivr.net/npm/chart.js@4.4.1/dist/chart.umd.min.js. Sem eixo y duplo; barra horizontal ordenada para ranking; linha para meses. - Cada cartão mostra "carregando" e, se a chamada falhar, uma mensagem com o status HTTP e a view, sem derrubar os outros cartões. - HTML, CSS e JS puros, sem build; funciona com python -m http.server e no GitHub Pages; sem rolagem horizontal no celular. Antes de escrever código, liste os arquivos e, para cada pergunta, a view, as colunas e a fórmula do título. Espere a minha aprovação.

Revisão humana do diff

  1. Há número digitado? Procure com grep -nE '[0-9]{2,}[.,][0-9]' aula-09-seunome/* e justifique cada ocorrência
  2. O erro aparece? Troque o nome de uma view no código e recarregue a página; apenas aquele cartão deve falhar
  3. O título afirma e vem do dado? Se a view mudar, a frase deve mudar junto
  4. Unidade, período e fonte estão em todos os cartões?

O diff é aceito somente quando as quatro respostas forem afirmativas.

Publicação no GitHub Pages

  1. git add, git commit e git push da pasta aula-09-seunome
  2. No seu fork, abra Settings e, em seguida, Pages
  3. Em Source, escolha Deploy from a branch; em Branch, selecione main e a pasta /(root); depois, clique em Save
  4. Aguarde o término do pages build and deployment na aba Actions
https://<usuario>.github.io/<repo>/aula-09-seunome/

Abra o endereço no celular, fora do Codespace. Esse teste reproduz a condição em que o board acessará o painel.

Diagnóstico de erros comuns

401
Chave errada, incompleta ou de outro projeto
404 PGRST205
View inexistente ou cache da API: notify pgrst, 'reload schema';
200 com []
RLS ligado sem política de leitura: confira o final de estrela.sql
404 do Pages
Caminho ou maiúscula errada, ou o deploy ainda está rodando
CORS
Em geral, indica URL errada, pois a API do Supabase aceita qualquer origem
Sem Pages
Repositório privado no plano gratuito; o fork precisa ser público

Teste de leitura em voz alta

  • Outro grupo abre a sua URL no celular, sem receber explicação
  • O grupo lê cada cartão em uma frase, e você anota a frase literal, entre aspas
  • Cada frase que ultrapassa o que o dado autoriza gera um ajuste na tela
  • Registre a divergência como âncora, com os cinco campos das aulas 7 e 8 (passo, leitura do usuário, o que o dado autoriza, consequência e suporte na tela), no frame do dashboard no quadro do Miro

Durante o teste, o autor não explica nem defende o painel, pois essa também será a condição de leitura no board.

A recomendação ao Chief de Vendas

Recomendação: atacar o prazo no RJ antes de subsidiar frete no Nordeste.

Número que sustenta: RJ tem 12.312 entregas e 12,2% com atraso; com atraso, a nota média cai para 2,27.

O que a invalidaria: se o atraso do RJ vier de poucos vendedores, a ação deve recair sobre esses sellers, e não sobre a promessa de prazo.

A recomendação só é aceita quando traz o número que a sustenta e a condição que a invalidaria.
