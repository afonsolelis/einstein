Do banco de treino ao banco real

Até aqui praticamos em uma base sintética com dezenas de linhas. Hoje a base é a Olist: um marketplace brasileiro, ~100 mil pedidos entre 2016 e 2018, com preço, frete, prazo prometido e realizado, pagamento, avaliação e geografia.

Dado real chega sujo, incompleto e ambíguo. Aprender a perguntar a ele é o objetivo da aula.

O mapa do Olist

olist_customers │ ▼ olist_orders ─────────────► olist_order_reviews │ ├──► olist_order_payments (1 pedido : N parcelas) │ └──► olist_order_items (1 pedido : N itens) │ │ ▼ ▼ olist_products olist_sellers

O pedido é o centro do modelo: quase toda pergunta passa por olist_orders.

Grão: o conceito da aula

  • olist_orders · uma linha é um pedido.
  • olist_order_items · uma linha é um item.
  • olist_order_payments · uma linha é uma parcela.

Ao juntar tabelas, o resultado assume o grão mais fino. Contar linhas depois de um JOIN e chamar isso de “total de pedidos” infla o número sem parecer errado.

Rodada 0 · reconhecer sem escrever SQL

  • Browse data → navegue pelas nove tabelas e leia as colunas.
  • X-ray → gere uma exploração automática de olist_orders.
  • Anote: quantas linhas, que período cobre, quais colunas têm nulo.

Trate o X-ray como bússola, não como resposta: ele mostra o que é fácil, não o que importa.

Rodada 1 · o primeiro SELECT

SELECT order_id, order_status, order_purchase_timestamp FROM olist_orders LIMIT 10;

Abra New → SQL query, escolha o banco Olist e execute. Leia na ordem lógica: origem, filtro, projeção, limite.

DQL · filtrar e ordenar

SELECT order_id, price, freight_value FROM olist_order_items WHERE price >= 500 ORDER BY price DESC LIMIT 20;

Confira: todas as linhas satisfazem o critério? O que ficou deliberadamente de fora?

Perfilar completude

SELECT order_status, COUNT(*) AS pedidos, COUNT(order_delivered_customer_date) AS com_entrega FROM olist_orders GROUP BY order_status ORDER BY pedidos DESC;

O nulo nunca é aleatório. Onde ele se concentra, existe uma regra de negócio.

Checkpoint · perfilamento

  • Quantos pedidos existem e em que período?
  • Quais status aparecem e com que peso?
  • Onde os nulos se concentram — e por quê?
  • Qual coluna é categoria e qual é identificador?

Rodada 2 · GROUP BY

SELECT c.customer_state, COUNT(*) AS pedidos, ROUND(AVG(i.price)::numeric, 2) AS ticket_medio FROM olist_orders AS o JOIN olist_customers AS c ON c.customer_id = o.customer_id JOIN olist_order_items AS i ON i.order_id = o.order_id GROUP BY c.customer_state ORDER BY pedidos DESC;

GROUP BY muda a granularidade: cada linha passa a representar um estado.

DQL · série temporal

SELECT date_trunc('month', order_purchase_timestamp) AS mes, COUNT(*) AS pedidos FROM olist_orders WHERE order_status = 'delivered' GROUP BY 1 ORDER BY 1;

As pontas da série quase sempre são meses incompletos. Um crescimento que “despenca” no fim costuma ser recorte, não queda.

Média ou mediana?

  • Preço e frete têm cauda longa: poucos valores altos puxam a média.
  • Use média quando a soma precisa ser preservada.
  • Use mediana para descrever o caso típico.
  • Média e mediana muito distantes não é problema a esconder: é achado a reportar.

Rodada 3 · JOIN com tradução

SELECT t.product_category_name_english AS categoria, COUNT(*) AS itens, ROUND(SUM(i.price)::numeric, 2) AS receita FROM olist_order_items AS i JOIN olist_products AS p ON p.product_id = i.product_id LEFT JOIN product_category_name_translation AS t ON t.product_category_name = p.product_category_name GROUP BY 1 ORDER BY receita DESC LIMIT 15;

O JOIN multiplicou linhas?

SELECT COUNT(*) AS linhas, COUNT(DISTINCT o.order_id) AS pedidos FROM olist_orders AS o JOIN olist_order_items AS i ON i.order_id = o.order_id;

Se linhas > pedidos, o grão mudou. Conte com COUNT(DISTINCT …) ou agregue antes de juntar.

Checkpoint · JOIN

  • O que uma linha representa agora?
  • O JOIN multiplicou registros?
  • Os filtros foram aplicados antes da agregação?
  • Você consegue explicar o número em uma frase?

Fechamento · três perguntas, três gráficos

Cada pergunta vira uma consulta salva, com o gráfico adequado à sua forma:

  • 1 · Como evoluiu o volume de pedidos entregues ao longo do tempo? → linha
  • 2 · Quais categorias concentram as piores avaliações? → barras
  • 3 · Onde a entrega atrasa mais em relação ao prazo prometido? → mapa ou barras

No fim, as três entram em um dashboard.

Pergunta 1 · pedidos entregues por mês

SELECT date_trunc('month', order_purchase_timestamp) AS mes, COUNT(*) AS pedidos FROM olist_orders WHERE order_status = 'delivered' GROUP BY 1 ORDER BY 1;

Visualization → Line. Série temporal pede linha. Nomeie a pergunta “Pedidos entregues por mês” e salve na sua coleção.

Pergunta 2 · piores avaliações por categoria

WITH pedido_categoria AS ( SELECT DISTINCT i.order_id, p.product_category_name FROM olist_order_items AS i JOIN olist_products AS p ON p.product_id = i.product_id ) SELECT COALESCE(t.product_category_name_english, pc.product_category_name) AS categoria, COUNT(*) AS pedidos, ROUND(AVG(r.review_score)::numeric, 2) AS nota_media FROM pedido_categoria AS pc JOIN olist_order_reviews AS r ON r.order_id = pc.order_id LEFT JOIN product_category_name_translation AS t ON t.product_category_name = pc.product_category_name GROUP BY 1 HAVING COUNT(*) >= 500 ORDER BY nota_media LIMIT 10;

Visualization → Bar. O DISTINCT na CTE evita que o JOIN com itens conte a mesma avaliação várias vezes.

Pergunta 3 · atraso por estado

SELECT c.customer_state, COUNT(*) AS pedidos, ROUND(100.0 * COUNT(*) FILTER ( WHERE o.order_delivered_customer_date > o.order_estimated_delivery_date ) / COUNT(*), 1) AS pct_atrasado FROM olist_orders AS o JOIN olist_customers AS c ON c.customer_id = o.customer_id WHERE o.order_status = 'delivered' AND o.order_delivered_customer_date IS NOT NULL GROUP BY c.customer_state ORDER BY pct_atrasado DESC;

Visualization → Map (region map por estado) ou Bar. Percentual comparável entre estados; o volume evita ler um estado com poucos pedidos como tendência.

Monte o dashboard

  1. New → Dashboard, nome “Painel Olist · seu nome”, dentro da sua coleção.
  2. Adicione as três perguntas salvas e ajuste o tamanho dos cards.
  3. Inclua um text card no topo com a leitura que o painel sustenta.
  4. Adicione um filtro de estado ou de período e conecte-o aos cards que aceitarem.

O que faz um painel valer a pena

  • Cada gráfico responde a uma pergunta enunciável em uma frase.
  • O título diz o achado, não a tabela de origem.
  • O eixo tem unidade explícita: pedidos, reais, percentual.
  • Se nenhuma decisão muda com o painel, ele é curiosidade — não painel.

Como organizar o trabalho

  • Crie uma coleção com o seu nome completo e salve tudo dentro dela.
  • Salve antes de mudar de tela — não há rascunho automático.
  • Nomeie a pergunta pelo conteúdo, não por “Pergunta 1”.
  • Não edite a coleção de um colega: use Duplicate.

Estrutura, pergunta e grão

  • Reconhecer vem antes de consultar.
  • DQL transforma dados em respostas.
  • Grão é o que separa um número certo de um número inflado.
  • Validação separa uma consulta executada de uma consulta confiável.
